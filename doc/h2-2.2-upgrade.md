# H2-Upgrade auf 2.2.224

## Zusammenfassung

Dieser Branch ersetzt die H2-Datenbank 2.1.214 durch 2.2.224, das letzte Release
der 2.2-Serie. Es enthält die Fehlerbehebungen aus 2.2.220 bis 2.2.224,
insbesondere die Behebung einer Race Condition im MVStore, die Datenkorruption
verursachen konnte (2.2.222). Die einzige inkompatible Änderung für den
CCU-Historian betrifft das Admin-Passwort der H2-Web-Konsole: Es darf seit
2.2.220 nicht mehr im Klartext übergeben oder abgelegt werden, sondern nur noch
als Salted-SHA-256-Hash. Der Patch in Database.groovy setzt das um.

## Zwingende Anpassungen

### Web-Konsolen-Passwort als Hash (CVE-2022-45868, PR #3833)

H2 2.2.220 lehnt Klartextwerte für -webAdminPassword mit einer
IllegalArgumentException ab. Gefordert ist das Ergebnis von
org.h2.server.web.WebServer.encodeAdminPassword(String): ein zufälliges Salt
zusammen mit dem SHA-256-Hash des gesalzenen Passworts, hexadezimal kodiert
(128 Zeichen). Hintergrund ist CVE-2022-45868: Ein über die Kommandozeile
übergebenes Klartext-Passwort war in der Prozessliste für lokale Benutzer
lesbar.

Bisher übergab Database.groovy (connect()) config.password unmittelbar an die
Option -webAdminPassword. Der Patch ruft nun
WebServer.encodeAdminPassword(config.password) auf und übergibt nur noch den
Hash an Server.createWebServer(). Das Passwort wird nicht reversibel
verschlüsselt, sondern gehasht abgelegt und verglichen.

### Mindestlänge 12 Zeichen

encodeAdminPassword() akzeptiert nur Passwörter mit mindestens 12 Zeichen
(Constants.MIN_WEB_ADMIN_PASSWORD_LENGTH=12). Da config.password zugleich
JDBC-Passwort und Web-Konsolen-Passwort ist, prüft Database.groovy die Länge
vor dem Start des Web-Servers und bricht bei kürzeren Passwörtern mit einer
klaren Fehlermeldung ab. Die Prüfung greift nur bei database.webEnable=true.
Das Standard-Passwort ccu-historian ist 13 Zeichen lang und bleibt verwendbar.
Die Beispiel-Konfiguration weist auf die Mindestlänge hin.

### Bibliothek und Build

ccu-historian/.classpath referenziert nun
external-libs/h2-2.2.224/h2-2.2.224.jar. Das ist die einzige Referenz auf die
H2-Version im Repository; die Ant-Builds kopieren alle im Eclipse-Classpath
referenzierten Jars nach build/lib (build-jar.xml), Start-Skripte und
Distributionen benötigen keine Anpassung.

Das Jar ist eine Binärdatei und nicht Teil dieses Branches. Beschaffung und
SHA-1-Prüfsumme stehen in external-libs/h2-2.2.224/README.md (Maven Central,
com.h2database:h2:2.2.224, Dual-Lizenz EPL 1.0/MPL 2.0). Die vorhandene
H2-Lizenzdatei ist versionsunabhängig; in external-libs/h2-2.2.224/LICENSE.txt
liegt die Redistribution-Notiz.

## Kompatibilitätsuntersuchung

### Java-Laufzeit

Projektbasis ist JavaSE-11 (.classpath), das CCU-Startskript verwendet
/opt/java/bin/java. H2 2.2.224 läuft ab Java 8; die Anforderung von Java 11
gilt erst für die 2.3-Serie. Keine Anpassung erforderlich.

### JDBC-URL

jdbc:h2:file:...;MODE=PostgreSQL;DB_CLOSE_ON_EXIT=FALSE;BUILTIN_ALIAS_OVERRIDE=TRUE
bleibt unverändert:

- MODE=PostgreSQL: weiterhin unterstützt; legitimiert auch VARCHAR ohne
  Längenangabe (Spalten TABLE_NAME, CUSTOM und andere).
- DB_CLOSE_ON_EXIT=FALSE: weiterhin unterstützt. PR #3846 (2.2.222, Make
  DB_CLOSE_ON_EXIT safer) ändert nur das Verhalten bei TRUE. Der Historian
  schließt die Datenbank explizit.
- BUILTIN_ALIAS_OVERRIDE=TRUE: auch in H2 2.2 vorhanden. Die eigenen Aliase
  TS_TO_UNIX und UNIX_TO_TS (DatabaseExtensions.groovy) kollidieren nicht mit
  Built-in-Funktionen von 2.2; das Flag bleibt als Absicherung bestehen.

### SQL (DDL und DML)

- TS DATETIME: DATETIME ist auch in 2.2 ein Alias für TIMESTAMP (belegt durch
  die H2-Test-Suite, datatypes/timestamp.sql). Betroffen sind die Tabellen
  D_*/C_* und REPLACE_TEMP.
- INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, CREATE INDEX IF NOT EXISTS,
  CREATE CACHED TEMP TABLE: unverändert unterstützt.
- CREATE ALIAS IF NOT EXISTS ... DETERMINISTIC FOR "...": unverändert.
- Backup per SCRIPT DROP TO ... COMPRESSION ZIP/GZIP: unverändert.

### H2-Tools

Script, RunScript und DeleteDbFiles bleiben unverändert. Die Optionen
-options DROP und DROP SCHEMA PUBLIC (createScript) gelten weiter. Die Option
-options FROM_1X (runScript) ist in 2.2 weiterhin Teil der RUNSCRIPT-Grammatik
({ [QUIRKS_MODE] [VARIABLE_BINARY] | FROM_1X }); das Einspielen von
H2-1.x-Dumps bleibt möglich.

### JDBC-Zugang

Sql.newInstance(url, config.user, config.password, org.h2.Driver) bleibt
unverändert. H2 verlangt das Datenbank-Passwort im Klartext; die Hash-Pflicht
betrifft ausschließlich webAdminPassword. DatabaseConfig gibt das Passwort
beim Debug-Logging bereits nicht aus.

### Datenbankformat (wichtigste Verhaltensänderung)

Mit 2.2.220 wurde die Formatversion des Speichers erhöht (PR #3834). Eine mit
2.2 einmal geöffnete Datenbank kann mit 2.1.x nicht mehr gelesen werden. Vor
dem Upgrade ist daher zwingend ein Backup anzulegen (Kommandozeilenoption
-createscript bzw. Web-Konsole). Ein Rollback auf 2.1.214 ist nur durch
Zurückspielen dieses Backups möglich; ein Parallelbetrieb mit derselben
Datenbankdatei ist ausgeschlossen.

### Sicherheit

Mit dem Hash-Patch ist die hier relevante Form von CVE-2022-45868 adressiert:
Das Passwort erscheint nicht mehr im Klartext in der Prozessliste und liegt im
Web-Server nur noch als Salted-SHA-256-Hash vor. Empfehlungen:
webAllowOthers nur in vertrauenswürdigen Netzen aktivieren, Passwort mit
mindestens 12 Zeichen wählen.

## Vorschläge (nicht umgesetzt)

- Verschlüsselte Ablage von database.password in der Konfigurationsdatei: H2
  verlangt das JDBC-Passwort im Klartext; eine verschlüsselte Ablage (z.B. AES
  mit Schlüssel aus einer Umgebungsvariablen) wäre nur Verschleierung und
  würde Angreifer mit Zugriff auf die Konfiguration nicht aufhalten. Sie ließe
  sich nachrüsten, ohne H2-seitige Vorgaben zu verletzen.
- Ein späteres Upgrade auf die 2.3-Serie ist mit der bestehenden Java-11-Basis
  möglich; die Kompatibilität wäre dann erneut zu prüfen.

## Migrationsschritte

1. Backup der bestehenden Datenbank anlegen (-createscript bzw. Web-Konsole).
2. h2-2.2.224.jar nach external-libs/h2-2.2.224/ kopieren (SHA-1 siehe
   README.md).
3. Projekt neu bauen und wie gewohnt deployen.
4. Beim ersten Start öffnet H2 die Datenbank und stellt sie auf das
   2.2-Format um.
